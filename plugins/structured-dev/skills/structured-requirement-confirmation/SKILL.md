## 操作核心规范

重要: 任务分为4个阶段：0：影响范围分析，1：复杂度判定 & 需求澄清(提问方式)，2：代码修改（根据类型执行对应流程），3：总结。
重要：该技能针对中低复杂度需求，通过提问方式澄清需求；高复杂度需求推荐使用Plan Agent(Plan Mode)写出完整需求计划。

## ❌ 不触发场景

以下场景**不触发**本技能：
- 代码阅读/理解："看看这个文件做什么"
- 问题诊断："帮我分析这个bug"
- 搜索定位："找到登录相关代码"
- 知识问答："什么是虚拟列表"
- 文档编写：非代码类文档

**触发判断：** 用户是否请求**修改代码文件**？是 → 触发；否 → 不触发。

## ⚡ 触发后立即执行

技能触发后，**立即**执行阶段0，不要先解释"技能被触发"：

1. 搜索相关文件，分析依赖关系
2. 输出 "## 🔍 影响范围分析报告"
3. 使用 AskUserQuestion 等待用户确认

## 工作流程

```
用户发起代码修改 → 阶段0(影响范围分析) → 阶段1(复杂度判定&需求澄清) → 阶段2(代码修改) → 阶段3(总结)
```

详见 `references/change-detection.md`（需求变更检测规则）
详见 `references/complexity-scoring.md`（复杂度评分指南）

## 阶段0：影响范围分析

**执行步骤**：识别所有受影响文件 → 分析依赖关系 → 按修改类型分类 → 等待用户确认

**简单任务（≤10分）：** 简化报告（文件清单 + 修改顺序）
**中等/复杂任务（≥11分）：** 标准报告（链路分析 + 修改类型判断）

---

## 阶段1：复杂度判定 & 需求澄清

### 5维问题扫描

| 维度 | 扫描目标 | 典型问题 |
|-----|---------|---------|
| 澄清定义 | 概念是否明确 | "优化性能"指什么？ |
| 挑战假设 | 隐式前提是否成立 | 所有用户都需要此功能？ |
| 探究证据 | 决策依据是否充分 | 为什么选方案A？ |
| 探索视角 | 是否考虑不同场景 | 移动端如何处理？ |
| 推演后果 | 实施后有何影响 | 对现有功能有何影响？ |

**评分规则从 `config/difficulty-rules.yaml` 读取。**

### 评分分支策略

- ≤10分（简单）: 提出 2-3 个问题
- 11-15分（中等）: 提出 3-5 个问题
- ≥16分（复杂）: 强烈推荐 Plan Agent

### 需求变更检测

| 检查项 | 类型A（独立新需求） | 类型B（修改当前需求） |
|--------|-------------------|---------------------|
| 共享核心组件？ | 不共享 | 共享 |
| 同一数据流？ | 独立数据流 | 同一数据流 |
| 同一迭代？ | 可独立交付 | 需要协同 |
| 业务目标独立？ | 独立 | 同一目标 |

## 阶段2：代码修改

### 多链路执行策略

| 链路数量 | 执行策略 |
|---------|---------|
| = 1条 | 单线程执行 |
| ≥ 2条 无依赖 | Agent Team 并行执行 |
| ≥ 2条 有依赖 | 顺序执行（Bug修复→重构→新需求） |

### 修改类型

| 类型 | 适用场景 |
|------|---------|
| 代码重构 | 文件重组、函数提取、格式化 |
| 新需求开发 | 新增API、组件、页面 |
| Bug修复 | 功能异常、性能问题 |

---

## 阶段3：总结

- 输出最终交付报告（修改文件清单、变更摘要、测试结果）
- 提醒用户验收要点
- 保存关键决策到 memory

## 关键陷阱提醒

1. 只修改当前文件 → 扩展分析依赖
2. "需求很明显" → 执行 5 维度扫描
3. 时间压力跳过阶段 → 时间压力更需要精确性
4. "你自己决定" → 提出选项获批准
5. 未区分变更类型 → 阶段1后必须判断A/B
6. 评分累加 → 只对独立需求评判，不累加
