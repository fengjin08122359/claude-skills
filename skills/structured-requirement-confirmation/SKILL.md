## 操作核心规范

重要: 任务分为4个阶段：0：影响范围分析，1：复杂度判定 & 需求澄清(提问方式)，2：代码修改（根据类型执行对应流程），3：总结。
重要：该技能针对中低复杂度需求，通过提问方式澄清需求；高复杂度需求推荐使用Plan Agent(Plan Mode)写出完整需求计划，由用户评论需求文档的方式整理完整实现方案。
重要: `structured-requirement-confirmation`技能与`superpower:brainstorming`类技能完全冲突，请勿同时使用。


## ❌ 不触发场景（否定测试）

以下场景**不触发**本技能：
- 代码阅读/理解："看看这个文件做什么"、"帮我理解这段代码"
- 问题诊断："帮我分析这个bug"、"为什么报错"
- 搜索定位："找到登录相关代码"、"搜索XXX函数"
- 知识问答："什么是虚拟列表"、"怎么用dayjs"
- 文档编写：非代码类文档、注释说明

**触发判断：** 用户是否请求**修改代码文件**？是 → 触发；否 → 不触发。

## ⚡ 触发后立即执行

技能触发后，**立即**执行阶段0，不要先解释"技能被触发"：

1. 搜索相关文件，分析依赖关系
2. 输出 "## 🔍 影响范围分析报告"
3. 使用 AskUserQuestion 等待用户确认

**禁止的行为：**
- 先输出"Skill triggered"说明 → 应直接开始执行
- 跳过阶段0直接问问题 → 必须先分析影响范围
- 因权限问题停止 → 应说明需要什么权限并继续流程框架

## 核心理念

**系统性保障，而非教条性流程。**

每个阶段解决实际问题：遗漏文件、需求误解、返工风险。

**特别需要使用的场景：**
- "快速改一下"、"简单修改"、只提到一个文件、任务看起来很明显、"我已经分析过了"、时间压力

这些场景最容易遗漏依赖或误解需求。

## 工作流程

```mermaid
graph TD
    Start([用户发起代码修改]) --> S0[阶段0: 影响范围分析]
    S0 --> S0_Out[输出: 文件清单 + 依赖关系]
    S0_Out --> S0_Confirm{用户确认?}
    S0_Confirm -- 修改 --> S0_Out
    S0_Confirm -- 确认 --> S1[阶段1: 复杂度判定 & 需求澄清]
    S1 --> Score[5维度评分]
    Score --> Score_Branch{总分≥16?}
    Score_Branch -- 是 --> Plan_Offer[推荐使用Plan Agent(Plan Mode)写出完整需求计划]
    Plan_Offer --> Plan_Choice{用户选择?}
    Plan_Choice -- 转用 --> Plan_End([结束本流程])
    Plan_Choice -- 继续 --> S1_Questions
    Score_Branch -- 否 --> S1_Questions[批量提出2-7个澄清问题]
    S1_Questions --> S1_Wait[等待用户回复]
    S1_Wait --> S1_Reply{用户回复}
    S1_Reply -- 仅回答 --> CodeMod[代码修改: 按类型执行]
    S1_Reply -- 新内容/变更 --> Change_Detect{需求变更检测}
    Change_Detect --> Check_Type[使用4问检查清单]
    Check_Type --> Type_Result{变更类型?}
    Type_Result -- 类型A: 独立新需求 --> TypeA_Notify[告知分离需求]
    TypeA_Notify --> TypeA_Choice{用户选择?}
    TypeA_Choice -- 完成当前 --> CodeMod
    TypeA_Choice -- 暂停当前 --> TypeA_Suspend[输出暂停状态] --> Start
    Type_Result -- 类型B: 修改当前需求 --> TypeB_Merge[合并需求]
    TypeB_Merge --> TypeB_Rescore[重新评分] --> S0_Out
    S1_Reply -- 发现矛盾/重新分析 --> S0_Back[回到阶段0重新分析] --> S0
    CodeMod --> CodeMod_Execute[执行对应类型流程]
    CodeMod_Execute --> CodeMod_Verify{所有测试通过?}
    CodeMod_Verify -- 否 --> CodeMod_Fix[修复问题] --> CodeMod_Execute
    CodeMod_Verify -- 是 --> S3[阶段3: 总结]
    S3 --> Complete([🎉 流程完成])
    Complete --> NewTask{新需求?}
    NewTask -- 是 --> Start
    NewTask -- 否 --> End([结束])
```

**流程关键点：**
- 阶段0→1→2→3 标准顺序执行
- **阶段1可回到阶段0**：发现矛盾或需要重新分析时，用户可要求回到阶段0
- 阶段1后必须检测需求变更（类型A/B）
- 类型A：完成当前流程，建议稍后开启新流程
- 类型B：合并需求，重新从阶段0开始
- 复杂度评分只针对独立需求评判(类型A)，不累加

## 阶段1：复杂度判定 & 需求澄清(提问方式)

### 问题生成流程

**核心流程：需求分解 → 5维度扫描 → 识别核心矛盾 → 设计问题列表**

1. **需求分解**：将用户需求拆解为技术实现要素
2. **5维度扫描**：系统化检查每个要素的清晰度
3. **识别核心矛盾**：定位真正需要用户决策的分歧点
4. **设计问题列表**：针对核心矛盾设计澄清问题

### 5维问题扫描框架

| 维度 | 扫描目标 | 典型问题 |
|-----|---------|---------|
| **澄清定义** | 概念是否明确 | "优化性能"指什么？加载速度？渲染帧率？内存占用？ |
| **挑战假设** | 隐式前提是否成立 | 是否所有用户都需要此功能？老数据如何迁移？ |
| **探究证据** | 决策依据是否充分 | 为什么选择方案A而非B？是否有性能数据支持？ |
| **探索视角** | 是否考虑不同场景 | 移动端如何处理？离线场景如何？权限不足时如何？ |
| **推演后果** | 实施后有何影响 | 对现有功能有何影响？是否引入破坏性变更？性能成本？ |

**扫描原则：**
- 系统化覆盖所有维度，不遗漏盲区
- 每个维度2-3个检查点，快速定位不确定性
- 只关注**真正需要用户决策**的点，跳过显而易见的实现细节

### 5维问题复杂度评分

| 维度 | 评分标准 |
|-----|---------|
| 文件数量 | 1-2个(1分) / 3-5个(3分) / 6+个(5分) |
| 依赖复杂度 | 独立模块(1分) / 2-3模块交互(3分) / 4+模块或核心架构(5分) |
| 需求明确度 | 非常清晰(1分) / 2-3模糊点(3分) / 4+模糊点(5分) |
| 技术风险 | 常规实现(1分) / 新技术或重构(3分) / 架构变更(5分) |
| 业务复杂度 | 简单增删改(1分) / 业务规则变更(3分) / 核心流程(5分) |

**总分 = 文件 + 依赖 + 需求 + 技术 + 业务**

**评分分支策略：**
- ≤10分（简单）: 继续本技能，提出2-3个问题
- 11-15分（中等）: 继续本技能，提出3-5个问题
- ≥16分（复杂）: **强烈推荐 Plan Agent**（给出具体理由：文件数、依赖复杂度、风险点）
  - 用户选择 Plan Agent → 结束本流程，转用 Plan Mode
  - 用户坚持继续本技能 → 只提**3-5个关键决策点**问题（不全面扫描），并明确提示风险

### 5维度扫描实战示例

**用户需求：优化列表加载性能**

**需求分解：**
- 数据获取方式（API调用、数据量）
- 渲染机制（虚拟列表、懒加载）
- 缓存策略（前端缓存、增量更新）
- 降级方案（网络失败、数据为空）

**5维度扫描过程（过程仅思考分析使用，输出展示核心矛盾结果即可）：**

```
1️⣣ 澄清定义

  → 检查点：大数据量列表？所有列表都优化？只优化核心场景？
```

- 优化范围不清晰（全局 vs 局部）
- 技术方案未确定（虚拟列表 vs 分页加载）

## 🔄 需求变更处理（阶段1后）

### 判断检查清单（必须全部回答）：

1. **是否共享核心组件？**
   - 类型A：不共享（ListComponent vs AvatarUpload）
   - 类型B：共享（ListComponent 和 SortComponent 共享 ListService）

2. **是否影响同一数据流？**
   - 类型A：独立数据流（列表数据 vs 用户头像数据）
   - 类型B：同一数据流（列表加载和列表排序都操作列表数据）

3. **是否需要在同一迭代完成？**
   - 类型A：可独立交付（用户可以分开验收）
   - 类型B：需要协同实现（用户期望一起交付）

4. **业务目标是否独立？**
   - 类型A：独立业务价值（性能优化 vs 功能新增）
   - 类型B：同一业务目标（都是列表功能的一部分）

**判断规则：**
- 几个问题全部回答"是" → 类型A
- 任意1个问题回答"否" → 类型B

### 类型A：新需求（独立需求）

**特征：** 与当前需求完全无关的新功能、不共享文件依赖、独立的业务目标和技术实现

**处理路径：**
1. 明确告知用户：检测到新需求，建议先完成当前任务
2. 完成当前流程：继续执行代码修改
3. 新需求处理建议：流程结束后，提醒用户开启新流程处理新需求

**输出格式：**

```markdown
## ✅ 检测到新需求

### 📋 需求分类

**当前需求：** [一句话描述当前任务]
**新需求：** [一句话描述新任务]

**独立性判断：**
- 两个需求不共享文件依赖
- 技术实现路径不同
- 业务目标独立

### 🔄 处理建议

1. **当前需求**：继续完成当前流程（执行代码修改）
2. **新需求**：当前任务完成后，重新使用本技能开启新流程

**请选择：**
- **选项A**：继续完成当前任务，新需求稍后处理（推荐）
- **选项B**：立即暂停当前任务，优先处理新需求
```

### 类型B：修改当前需求（关联需求）

**特征：** 对当前需求的补充/细化/修正、共享文件依赖、扩大或缩小当前需求范围、改变技术实现方式

**处理路径：**
1. 合并需求描述：将新旧需求合并为统一的描述
2. 重新执行阶段0：完整的重新分析影响范围
3. 重新评分复杂度：只针对合并后的独立需求评判（不累加）
4. 重新执行阶段1：针对变更部分批量提问

**输出格式：**

```markdown
## ⚠️ 需求变更检测（修改当前需求）

### 🔄 需求合并

**原需求：** [一句话描述]
**变更内容：** [用户提出的修改]
**合并需求：** [合并后的完整需求描述]

**变更点：**
- ✚ 补充：[具体补充内容]
- ✎ 修改：[具体修改内容]
- ✖ 删除：[具体删除内容]

### 🔄 重新执行影响分析
由于需求修改，我将重新执行阶段0的完整分析流程...

[继续输出新的阶段0报告]

### 📊 复杂度重新评分
对合并后的独立需求重新进行5维度评分：
文件[评分] + 依赖[评分] + 需求[评分] + 技术[评分] + 业务[评分] = **总分 [总分]/25**

⚠️ 注意：复杂度评分只针对一个独立的合并需求评判，不累加评分。
```

### 复杂度评分规则

**重要规则：只针对一个独立需求评判**
- **不累加评分**：多个需求合并时，重新评估合并后的整体复杂度
- **不分开评分**：一个独立需求只评分一次，反映整体复杂度
- **需求合并时重新评分**：当类型B需求变更时，重新对合并后的需求评分

**错误做法：** 原需求13分 + 新需求5分 = 总分18分（❌ 错误累加）
**正确做法：** 合并需求重新评估 → 16分（✓ 整体评估）

### 常见判断案例

| 用户回复示例 | 变更类型 | 判断依据 | 处理方式 |
|------------|---------|---------|---------|
| "顺便加个搜索功能" | 类型A | 搜索与列表优化是独立功能，不共享依赖 | 完成当前→新流程 |
| "列表还需要支持排序" | 类型B | 排序是列表功能的扩展，共享列表组件 | 合并需求→重新执行 |
| "优化登录页加载速度" → "还要实现头像上传" | 类型A | 登录优化与头像上传不共享文件 | 完成当前→新流程 |
| "优化登录页加载速度" → "登录失败时显示验证码" | 类型B | 验证码是登录流程的一部分 | 合并需求→重新执行 |
| "添加用户管理API" → "用RESTful风格" | 类型B | 技术方案变更，但仍是一个任务 | 合并需求→重新执行 |
| "修复登录bug" → "顺便优化注册流程" | 类型A | 登录与注册是独立流程 | 完成当前→新流程 |

## 阶段2：代码修改

### 🔀 多链路执行策略判断

**步骤1：检查链路数量**

| 链路数量 | 执行策略 | 说明 |
|---------|---------|------|
| **= 1条** | 单线程执行 | 直接加载对应类型流程文件执行 |
| **≥ 2条** | 需检测依赖 | 进一步判断是否可并行 |

---

**步骤2：链路依赖检测（链路数 ≥ 2时执行）**

分析各链路之间是否存在交叉依赖：

```markdown
## 🔗 链路依赖检测

### 检测维度

| 检测项 | 检测方法 | 有依赖示例 |
|-------|---------|-----------|
| **共享文件** | 各链路文件清单是否有交集 | 链路1修改 fileA.ts，链路2也修改 fileA.ts |
| **数据流依赖** | 一个链路的输出是另一个的输入 | 链路1新增API，链路2的组件需调用该API |
| **导入依赖** | 修改会影响其他链路的导入路径 | 链路1重构移动文件，链路2的导入路径需更新 |
| **状态依赖** | 共享状态管理 | 链路1修改 store，链路2依赖同一 store |

### 检测结果输出

| 链路组合 | 共享文件 | 数据流依赖 | 导入依赖 | 状态依赖 | 结论 |
|---------|---------|-----------|---------|---------|------|
| 链路1-链路2 | ✅ fileA.ts | ❌ | ✅ | ❌ | **有依赖** |
| 链路1-链路3 | ❌ | ❌ | ❌ | ❌ | **无依赖** |
| 链路2-链路3 | ❌ | ✅ | ❌ | ❌ | **有依赖** |
```

---

**步骤3：根据检测结果选择执行方式**

| 检测结果 | 执行方式 | 说明 |
|---------|---------|------|
| **所有链路无依赖** | Agent Team 并行执行 | 多个子agent同时处理，主agent汇总 |
| **存在任意依赖** | 顺序执行 | 按优先级排序，逐条链路执行 |

### 单链路执行（链路数 = 1 或 有依赖的多链路顺序执行）

直接加载对应类型流程文件执行：

| 修改类型 | 适用场景 | 详细流程 |
|---------|---------|---------|
| **代码重构** | 文件重组、函数提取、格式化、类型重构 | [code-modification-refactor.md](code-modification-refactor.md) |
| **新需求开发** | 新增API、组件、页面、业务逻辑 | [code-modification-new-feature.md](code-modification-new-feature.md) |
| **Bug修复** | 功能异常、性能问题、安全漏洞修复 | [code-modification-bug-fix.md](code-modification-bug-fix.md) |

**选择原则：**
- 用户需求明确指定修改类型 → 使用对应流程
- 需求模糊或混合类型 → 默认使用代码重构流程

**顺序执行排序规则（有依赖时）：**

按优先级排序：Bug修复 → 代码重构 → 新需求开发

```markdown
## 📋 顺序执行计划

**依赖检测结果：** 链路间存在共享文件/数据流依赖

**执行顺序（按优先级）：**

| 序号 | 链路 | 修改类型 | 执行原因 |
|-----|-----|---------|---------|
| 1 | 链路A | Bug修复 | 优先修复，避免后续链路基于错误代码开发 |
| 2 | 链路B | 代码重构 | 重构后结构稳定，新需求基于重构后代码 |
| 3 | 链路C | 新需求开发 | 基于修复+重构后的稳定基础开发 |

**每条链路执行完后：**
- 更新后续链路的上下文（反映已完成的修改）
- 检查是否影响后续链路的计划，必要时调整
```

```markdown
| 冲突类型 | 处理方式 |
|---------|---------|
```

## 阶段3：总结

**流程完成后的收尾工作**

**执行内容：**
- 输出最终交付报告（修改文件清单、变更摘要、测试结果）
- 提醒用户验收要点
- 保存关键决策到用户记忆（如有必要）

**后续对话规则：**
⚠️ **阶段3结束后，如果用户继续对话提出新的修改请求，必须从阶段0重新开始完整流程。**

新需求 = 新任务 = 新流程（阶段0→1→2→3）

## 验证清单

- [ ] **阶段0**：文件清单确认
- [ ] **阶段1**：批量提问 + 用户确认 + 变更检测
- [ ] **阶段2**：测试通过
- [ ] **阶段3**：交付报告输出

**未完成？** 回到对应阶段继续。

## 关键陷阱提醒

1. 只修改当前文件 → 扩展分析依赖
2. "需求很明显" → 执行5维度扫描
3. 时间压力跳过阶段 → 时间压力更需要精确性
4. "你自己决定" → 提出选项获批准
5. 无回复就继续 → 等待或提MVP方案
6. 未区分变更类型 → 阶段1后必须判断A/B
7. 评分累加 → 只对独立需求评判，不累加

**记住：** 每个阶段解决实际问题：遗漏文件、需求误解、返工风险。跳过阶段 = 增加失败概率。
