# 任务拆解指南

本文档提供将复杂需求拆分为2小时任务单元的系统化方法。

## 核心原则

### 1. 时间盒原则(Timeboxing)

每个任务必须在 **2小时内可完成**,这是硬性约束。

**为什么是2小时?**
- 足够完成一个有意义的功能点
- 不会太长导致难以估算
- 便于进度跟踪和调整
- 符合注意力集中周期

**如果任务太大怎么办?**
```
原始任务: "实现用户管理系统" (预计8小时)

拆解后:
- Task 1: 设计用户数据模型 (1h)
- Task 2: 实现用户CRUD API (2h)
- Task 3: 创建用户列表页面 (1.5h)
- Task 4: 实现用户详情页面 (1.5h)
- Task 5: 添加用户编辑功能 (1.5h)
- Task 6: 编写单元测试 (1.5h)
```

### 2. 原子性原则

每个任务应该是**独立的、可验证的**。

**好的原子任务**:
- ✅ "创建User类型定义" - 独立、可验证
- ✅ "实现getUserList API方法" - 独立、可验证
- ❌ "实现用户管理" - 太宽泛,不可验证

**检查方法**:
- 能否在不依赖其他未完成任务的情况下完成?
- 完成后能否立即验证(运行测试/手动测试)?
- 是否有明确的交付物(代码/文档/配置)?

### 3. 依赖清晰原则

任务之间的依赖关系必须**明确标注**。

**依赖类型**:
- **硬依赖**: 必须先完成A才能开始B
- **软依赖**: B可以独立进行,但需要A的某些信息
- **无依赖**: 完全独立,可并行执行

**示例**:
```markdown
### Task 2: 实现用户列表API
**依赖任务**: Task 1 (用户类型定义)
**说明**: 需要Task 1定义的User类型

### Task 3: 创建用户列表页面
**依赖任务**: Task 2 (用户列表API)
**说明**: 需要调用Task 2实现的API
```

### 4. 验收标准原则

每个任务必须有**明确的验收标准**。

**验收标准应该**:
- 具体可测量
- 可自动化验证(优先)
- 覆盖正常和异常情况

**示例**:
```markdown
**验收标准**:
- [ ] API返回正确的数据结构
- [ ] 支持分页参数(page, pageSize)
- [ ] 支持排序参数(sortBy, order)
- [ ] 错误时返回标准错误格式
- [ ] 响应时间 < 500ms (1000条数据)
```

## 任务评估体系

### 评估维度

任务评估需要从多个维度综合考虑,确保估算的准确性。

#### 维度1: 技术复杂度 (Technical Complexity)

**评估因素**:
- **代码量**: 需要编写的代码行数
- **算法难度**: 是否涉及复杂算法或数据结构
- **技术栈熟悉度**: 对所用技术的熟悉程度
- **集成难度**: 与现有系统的集成复杂度
- **边界情况**: 需要处理的异常情况数量

**评分标准**:
```
低复杂度 (1分):
- 代码量 < 100行
- 使用熟悉的技术
- 简单的CRUD操作
- 边界情况少

中复杂度 (2分):
- 代码量 100-300行
- 需要学习少量新技术
- 涉及业务逻辑
- 有一定的边界情况

高复杂度 (3分):
- 代码量 > 300行
- 需要使用不熟悉的技术
- 涉及复杂算法
- 大量边界情况需要处理
```

**示例**:
```markdown
Task: 创建User类型定义
- 代码量: ~30行
- 技术: TypeScript (熟悉)
- 复杂度: 低 (1分)
- 估算: 0.5h

Task: 实现Excel导出功能
- 代码量: ~200行
- 技术: exceljs库 (需学习)
- 复杂度: 中 (2分)
- 估算: 2h

Task: 实现实时数据同步
- 代码量: ~400行
- 技术: WebSocket (不熟悉)
- 复杂度: 高 (3分)
- 估算: 需要拆分为多个任务
```

#### 维度2: 业务复杂度 (Business Complexity)

**评估因素**:
- **业务规则**: 业务逻辑的复杂程度
- **决策分支**: if-else/switch分支数量
- **状态管理**: 需要管理的状态数量
- **交互流程**: 用户交互的步骤数
- **权限控制**: 权限判断的复杂度

**评分标准**:
```
低复杂度 (1分):
- 业务规则简单明确
- 决策分支 < 3个
- 状态 < 5个
- 交互步骤 < 3步
- 无权限控制或简单权限

中复杂度 (2分):
- 业务规则有一定复杂性
- 决策分支 3-8个
- 状态 5-15个
- 交互步骤 3-8步
- 中等复杂度权限控制

高复杂度 (3分):
- 业务规则复杂,有多重约束
- 决策分支 > 8个
- 状态 > 15个
- 交互步骤 > 8步
- 复杂的多层权限控制
```

**示例**:
```markdown
Task: 实现用户登录
- 业务规则: 验证用户名密码
- 决策分支: 2个(成功/失败)
- 状态: 3个(loading, success, error)
- 交互: 1步(点击登录)
- 复杂度: 低 (1分)

Task: 实现组合审批流程
- 业务规则: 多级审批,条件分支
- 决策分支: 6个(不同审批结果)
- 状态: 10个(待审批/审批中/已通过等)
- 交互: 5步(提交→初审→复审→终审→归档)
- 复杂度: 中 (2分)
```

#### 维度3: 依赖复杂度 (Dependency Complexity)

**评估因素**:
- **外部依赖**: 依赖的外部系统/API数量
- **内部依赖**: 依赖的内部模块数量
- **数据依赖**: 需要处理的数据结构复杂度
- **时序依赖**: 是否有严格的执行顺序要求
- **环境依赖**: 是否需要特殊环境配置

**评分标准**:
```
低复杂度 (1分):
- 外部依赖: 0-1个
- 内部依赖: 0-2个
- 数据结构: 简单对象/数组
- 时序: 无严格要求
- 环境: 无需特殊配置

中复杂度 (2分):
- 外部依赖: 2-3个
- 内部依赖: 3-5个
- 数据结构: 嵌套对象/复杂查询
- 时序: 有一定顺序要求
- 环境: 需要简单配置

高复杂度 (3分):
- 外部依赖: > 3个
- 内部依赖: > 5个
- 数据结构: 多层嵌套/图结构
- 时序: 严格顺序,有并发控制
- 环境: 需要复杂配置
```

**示例**:
```markdown
Task: 实现本地数据过滤
- 外部依赖: 0
- 内部依赖: 1 (数据源)
- 数据结构: 数组过滤
- 复杂度: 低 (1分)

Task: 实现跨系统数据同步
- 外部依赖: 3 (用户中心/组合系统/通知系统)
- 内部依赖: 4 (API层/Service层/Store/Utils)
- 数据结构: 多表关联查询
- 复杂度: 高 (3分)
```

#### 维度4: 测试复杂度 (Testing Complexity)

**评估因素**:
- **测试用例数量**: 需要编写的测试用例数
- **Mock难度**: Mock外部依赖的难度
- **边界情况**: 需要覆盖的边界情况数量
- **集成测试**: 是否需要集成测试
- **性能测试**: 是否需要性能测试

**评分标准**:
```
低复杂度 (1分):
- 测试用例: < 5个
- Mock: 简单或无需Mock
- 边界情况: < 3个
- 仅需单元测试

中复杂度 (2分):
- 测试用例: 5-15个
- Mock: 需要Mock 2-3个依赖
- 边界情况: 3-8个
- 需要单元+部分集成测试

高复杂度 (3分):
- 测试用例: > 15个
- Mock: 需要Mock > 3个依赖
- 边界情况: > 8个
- 需要完整的单元+集成+性能测试
```

### 综合评估公式

**任务复杂度总分** = 技术复杂度 + 业务复杂度 + 依赖复杂度 + 测试复杂度

**总分范围**: 4-12分

**时间估算映射**:
```
4-5分:   0.5-1小时   (简单任务)
6-7分:   1-1.5小时   (中等简单任务)
8-9分:   1.5-2小时   (中等复杂任务)
10-11分: 2-3小时     (复杂任务,建议拆分)
12分:    3+小时      (非常复杂,必须拆分)
```

**示例计算**:
```markdown
Task: 实现组合列表导出功能

技术复杂度: 2分 (需要使用exceljs库,有一定学习成本)
业务复杂度: 1分 (业务逻辑简单,就是导出数据)
依赖复杂度: 2分 (依赖API接口和文件下载工具)
测试复杂度: 2分 (需要测试正常导出、空数据、大数据量等场景)

总分: 2+1+2+2 = 7分
估算时间: 1-1.5小时 → 调整为 1.5h (留有余量)
```

### 风险评估

除了复杂度评估,还需要评估风险等级。

#### 风险等级分类

**低风险 (Green)**:
- 使用成熟稳定的技术
- 有类似的成功案例参考
- 团队成员有经验
- 不涉及核心业务逻辑

**中风险 (Yellow)**:
- 使用较新的技术或库
- 有部分参考但不完全相同
- 团队经验有限
- 涉及重要业务逻辑

**高风险 (Red)**:
- 使用未经验证的新技术
- 无参考案例,需要探索
- 团队无相关经验
- 涉及核心业务,影响面大

**风险应对策略**:
```
低风险: 直接实施,预留10%缓冲时间
中风险: 先做小规模POC,预留20%缓冲时间
高风险: 必须先做预研任务,预留50%缓冲时间或拆分更多小任务
```

**示例**:
```markdown
Task: 集成成熟的图表库ECharts
- 风险等级: 低风险 (Green)
- 理由: ECharts成熟稳定,项目已有使用经验
- 缓冲: +10%时间

Task: 尝试新的WebSocket实时通信方案
- 风险等级: 中风险 (Yellow)
- 理由: 团队WebSocket经验有限
- 缓冲: +20%时间,先做POC验证

Task: 实现自定义渲染引擎
- 风险等级: 高风险 (Red)
- 理由: 无经验,无参考,技术难度大
- 缓冲: 拆分为预研+实现两个阶段
```

### 不确定性处理

对于不确定的任务,采用以下策略:

#### 策略1: 三点估算法

给出三个估算值:
- **乐观估计 (O)**: 一切顺利的最短时间
- **最可能估计 (M)**: 正常情况下的时间
- **悲观估计 (P)**: 遇到问题的最长时间

**最终估算** = (O + 4×M + P) / 6

**示例**:
```
任务: 实现复杂的表单验证

乐观: 1h (有现成方案,直接复用)
最可能: 2h (需要一些定制开发)
悲观: 4h (遇到兼容性问题,需要调试)

估算 = (1 + 4×2 + 4) / 6 = 13/6 ≈ 2.17h → 取 2.5h
```

#### 策略2: 分解估算法

将任务进一步分解为子步骤,分别估算后累加:

```
任务: 创建用户列表页面

子步骤:
- 搭建页面框架: 0.5h
- 实现数据加载: 0.5h
- 实现表格渲染: 0.5h
- 添加分页功能: 0.5h
- 添加筛选功能: 0.5h
- 编写测试: 0.5h

总计: 3h → 超过2h,需要拆分为2个任务
```

#### 策略3: 类比估算法

参考类似任务的历史数据:

```
历史数据:
- Task "用户列表" 实际耗时: 1.5h
- Task "角色列表" 复杂度相当

当前任务: "权限列表"
→ 估算: 1.5h (基于类比)
```

#### 策略4: 预研任务法

对于高度不确定的任务,先创建预研任务:

```markdown
### Task 1: 【预研】评估技术方案 (2h)

**目标**: 确定可行的技术方案
**交付物**: 技术方案对比文档 + POC代码
**后续**: 根据预研结果细化实施任务
```

## 常见评估错误

### ❌ 错误1: 过于乐观

**表现**: 只考虑理想情况,忽略问题和调试时间

**改进**: 
- 使用三点估算法
- 预留至少20%缓冲时间
- 考虑可能的技术问题

### ❌ 错误2: 忽视学习成本

**表现**: 假设自己对所有技术都熟悉

**改进**:
- 诚实评估技术熟悉度
- 为学习新技术预留时间
- 查找文档和示例的时间也要算进去

### ❌ 错误3: 低估测试时间

**表现**: 只估算开发时间,忽略测试时间

**改进**:
- 测试时间通常占20%-30%
- 复杂逻辑需要更多测试
- 包括编写测试和修复测试失败的时间

### ❌ 错误4: 忽略沟通成本

**表现**: 假设可以专注编码,不考虑会议、讨论等

**改进**:
- 每天最多安排6小时实际编码
- 预留时间用于代码审查、讨论
- 考虑上下文切换的成本

### ❌ 错误5: 一次性估算过大任务

**表现**: 直接估算8小时的大任务

**改进**:
- 强制拆分为≤2小时的任务
- 每个小任务单独估算
- 累加得到总时间

## 实践建议

### 建议1: 建立个人基准

记录自己完成各类任务的实际时间,建立个人基准:

```markdown
我的基准数据:
- 简单CRUD API: 1-1.5h
- Vue组件(中等): 1.5-2h
- 单元测试(10个用例): 1-1.5h
- Bug修复(简单): 0.5-1h
- Bug修复(复杂): 2-4h
```

### 建议2: 定期回顾和调整

每完成5-10个任务后:
- 对比预估时间和实际时间
- 分析偏差原因
- 调整估算系数

**示例**:
```
发现: 我的估算普遍偏乐观20%
调整: 所有估算 × 1.2
```

### 建议3: 分类统计

按任务类型分类统计准确率:

```markdown
任务类型        | 平均偏差 | 调整系数
---------------|---------|----------
API开发         | -15%    | × 1.15
UI组件          | -25%    | × 1.25
Bug修复         | +10%    | × 0.9
重构            | -30%    | × 1.30
```

### 建议4: 考虑上下文因素

同样的任务,在不同情况下耗时可能不同:

**影响因素**:
- 疲劳程度(下午效率可能降低)
- 干扰程度(会议多的日子效率低)
- 熟悉程度(刚接触的代码需要更多时间)
- 工具熟练度(新工具需要学习时间)

### 建议5: 持续改进

- 记录每次估算和实际耗时
- 分析偏差模式
- 不断优化估算方法
- 分享经验给团队

## 拆解方法论

### 方法1: 垂直切分(推荐)

按**功能模块**垂直切分,每个任务包含完整的前后端。

**适用场景**: 新功能开发

**示例**: "实现用户搜索功能"

```
❌ 水平切分(不推荐):
- Task 1: 实现所有后端API
- Task 2: 实现所有前端页面
- Task 3: 编写所有测试

✅ 垂直切分(推荐):
- Task 1: 实现搜索API + 搜索页面基础框架
- Task 2: 实现搜索结果展示 + 分页功能
- Task 3: 实现高级筛选功能
- Task 4: 添加搜索历史记录
- Task 5: 编写端到端测试
```

**优点**:
- 每个任务都可独立演示
- 便于增量开发和反馈
- 降低集成风险

### 方法2: 分层切分

按**技术层次**切分,先基础设施后业务逻辑。

**适用场景**: 大型重构或新架构引入

**示例**: "迁移到TypeScript"

```
- Task 1: 配置TypeScript编译环境
- Task 2: 为工具函数添加类型定义
- Task 3: 为API层添加类型定义
- Task 4: 为核心组件添加类型定义
- Task 5: 修复类型错误并启用严格模式
```

**优点**:
- 系统性推进,不易遗漏
- 逐步提升代码质量
- 便于团队协作分工

### 方法3: 用户故事切分

按**用户操作流程**切分,每个任务对应一个用户场景。

**适用场景**: 面向用户的功能开发

**示例**: "实现订单提交流程"

```
- Task 1: 购物车页面 - 用户查看待提交订单
- Task 2: 地址选择 - 用户选择收货地址
- Task 3: 支付方式 - 用户选择支付方式
- Task 4: 订单确认 - 用户确认订单信息
- Task 5: 提交订单 - 用户完成支付
- Task 6: 订单成功页 - 显示提交结果
```

**优点**:
- 贴合用户需求
- 便于产品验收
- 优先级清晰

### 方法4: 风险驱动切分

优先处理**高风险、高不确定性**的部分。

**适用场景**: 技术方案不明确的项目

**示例**: "集成新的图表库"

```
- Task 1: 【预研】评估3个候选图表库 (2h)
- Task 2: 【预研】POC验证选定库的核心功能 (2h)
- Task 3: 封装图表组件基础框架 (1.5h)
- Task 4: 实现柱状图组件 (1.5h)
- Task 5: 实现折线图组件 (1.5h)
- Task 6: 实现饼图组件 (1.5h)
```

**优点**:
- 早期发现技术风险
- 避免后期大规模返工
- 为后续任务提供确定性

## 拆解步骤

### Step 1: 理解需求全貌

**目标**: 建立对需求的整体认知

**行动**:
1. 阅读需求文档或与用户沟通
2. 识别核心功能点
3. 列出所有相关模块
4. 标记不确定和模糊的地方

**输出**: 需求要点清单

```markdown
- 功能点2: ...

### 相关模块
- 模块A: ...
- 模块B: ...

### 不确定点
- 问题1: ...
- 问题2: ...
```

### Step 2: 识别技术约束

**目标**: 了解项目的技术环境和限制

**行动**:
1. 检查现有技术栈
2. 查看相关代码实现
3. 识别依赖和约束
4. 评估技术风险

**目标**: 生成粗粒度的任务列表

**行动**:
1. 按功能模块分组

3. 不考虑时间粒度,先求全面

**目标**: 将任务调整为2小时粒度

**行动**:
1. 估算每个任务的耗时
2. 超过2小时的任务继续拆分
3. 小于30分钟的任务考虑合并
4. 标注任务依赖关系

**输出**: 细粒度任务列表

**目标**: 为每个任务制定明确的验收标准

**目标**: 确定任务执行顺序

**行动**:

## 常见模式和反模式

### ✅ 好的拆解模式

#### 模式1: API先行

```
Task 1: 定义API类型
Task 2: 实现API方法
Task 3: 创建业务Hook
Task 4: 开发UI组件
```

**优点**: 前后端解耦,可并行开发

#### 模式2: 骨架优先

```
Task 1: 搭建页面框架(空状态)
Task 2: 实现数据加载
Task 3: 实现交互逻辑
Task 4: 优化用户体验
```

**优点**: 快速看到效果,便于调整

#### 模式3: 核心优先

```
Task 1: 实现核心功能(MVP)
Task 2: 添加辅助功能
Task 3: 优化性能和体验
Task 4: 完善边缘情况
```

**优点**: 尽早交付可用版本

### ❌ 坏的拆解模式

#### 反模式1: 任务过大

```
❌ Task 1: 实现完整的用户管理系统 (8h)
```

**问题**: 难以估算,难以跟踪,风险高

**改进**: 拆分为4-6个小任务

#### 反模式2: 任务过细

```
❌ Task 1: 创建user.ts文件 (5min)
❌ Task 2: 添加import语句 (2min)
❌ Task 3: 定义User接口 (10min)
```

**问题**: 管理成本高,意义不大

**改进**: 合并为1-2个任务

#### 反模式3: 依赖混乱

```
❌ Task 3 依赖 Task 5
❌ Task 5 依赖 Task 2
❌ Task 2 依赖 Task 3
```

**问题**: 循环依赖,无法执行

**改进**: 重新设计任务顺序,消除循环

#### 反模式4: 验收标准模糊

```
❌ 验收标准: "功能正常工作"
```

**问题**: 无法客观验证

**改进**: "点击提交按钮后,显示成功提示,并在列表中新增一条记录"

## 特殊场景处理

### 场景1: 需求不明确

**策略**: 先做探索性任务

```
Task 1: 【探索】调研3种技术方案 (2h)
Task 2: 【探索】POC验证选定方案 (2h)
Task 3: 基于POC结果细化后续任务
```

### 场景2: 技术风险高

**策略**: 前置风险评估任务

```
Task 1: 【风险】评估第三方库兼容性 (1.5h)
Task 2: 【风险】验证性能瓶颈 (1.5h)
Task 3: 根据评估结果调整实施方案
```

### 场景3: 依赖外部团队

**策略**: 明确接口契约,并行开发

```
Task 1: 定义API接口规范 (1h)
Task 2: Mock API数据进行前端开发 (2h)
Task 3: 联调真实API (1h) - 等待后端完成
```

### 场景4: 遗留代码改造

**策略**: 渐进式重构,保持向后兼容

```
Task 1: 分析现有代码结构 (1.5h)
Task 2: 创建新组件(不修改旧代码) (2h)
Task 3: 逐步迁移使用方 (1.5h × N)
Task 4: 删除旧代码 (0.5h)
```

## 任务估算技巧

### 技巧1: 三点估算法

对于不确定的任务,给出三个估算:
- **乐观估计**: 一切顺利的情况
- **最可能估计**: 正常情况
- **悲观估计**: 遇到问题的情况

**最终估算** = (乐观 + 4×最可能 + 悲观) / 6

**示例**:
```
任务: 实现复杂的表单验证

乐观: 1h (有现成方案)
最可能: 2h (需要一些定制)
悲观: 4h (遇到兼容性问题)

估算 = (1 + 4×2 + 4) / 6 = 2.17h → 2h
```

### 技巧2: 类比估算

参考类似任务的历史数据

**示例**:
```
之前实现"用户列表"用了1.5h
现在实现"角色列表"复杂度相当
→ 估算1.5h
```

### 技巧3: 分解估算

将任务进一步分解为子步骤,分别估算后累加

**示例**:
```
任务: 创建用户列表页面

- 搭建页面框架: 0.5h
- 实现数据加载: 0.5h
- 实现表格渲染: 0.5h
- 添加分页功能: 0.5h
- 添加筛选功能: 0.5h
- 编写测试: 0.5h

总计: 3h → 拆分为2个任务
```

### 技巧4: 缓冲时间

为不确定性预留缓冲

**规则**:
- 熟悉的技术: 不加缓冲
- 一般熟悉: +20%缓冲
- 不熟悉: +50%缓冲或先做预研任务

## 任务优先级排序

### 优先级矩阵

```
                高价值    低价值
高成本    │  第二优先  │  最后考虑  │
低成本    │  第一优先  │  第三优先  │
```

**排序策略**:
1. **P0**: 高价值 + 低成本 - 立即执行
2. **P1**: 高价值 + 高成本 - 重点投入
3. **P2**: 低价值 + 低成本 - 有空再做
4. **P3**: 低价值 + 高成本 - 考虑放弃

### 关键路径法

识别**最长依赖链**,确保关键路径上的任务优先执行

**示例**:
```
关键路径: Task 1 → Task 3 → Task 5 → Task 7 (总耗时6h)
非关键: Task 2 → Task 4 (总耗时3h,可并行)

策略: 优先执行Task 1,同时启动Task 2
```

## 实践建议

### 建议1: 从简单开始

第一个任务应该:
- 相对简单,容易完成
- 能快速看到成果
- 为后续任务奠定基础

**好处**: 建立信心,验证方案可行性

### 建议2: 留出缓冲

不要把时间安排得太满

**规则**:
- 每天最多安排6小时的实际任务
- 留出2小时处理意外情况
- 每周留出半天做技术债务

### 建议3: 定期回顾

每完成3-5个任务后:
- 对比预估时间和实际时间
- 分析偏差原因
- 调整后续任务的估算

### 建议4: 保持灵活

- 接受中途调整
- 必要时重新拆解
- 不要固执于初始计划

### 建议5: 记录经验

建立自己的任务模板库:
- 记录成功的拆解模式
- 记录失败的教训
- 持续优化估算准确度

在完成任务拆解后,使用以下清单自检:

- [ ] 每个任务是否都能在2小时内完成?
- [ ] 每个任务是否有明确的验收标准?
- [ ] 任务依赖关系是否清晰?
- [ ] 是否存在循环依赖?
- [ ] 关键路径是否合理?
- [ ] 是否有足够的缓冲时间?
- [ ] 高风险任务是否前置?
- [ ] 是否覆盖了所有需求点?
- [ ] 验收标准是否可验证?
- [ ] 任务描述是否清晰无歧义?

如果有任何一项为"否",需要重新审视和调整。
