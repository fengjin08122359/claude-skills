# 任务复杂度评估快速参考

本文档提供任务复杂度评估的快速查询指南,帮助快速准确地估算任务时间。

## 🎯 评估流程

```
1. 分析任务 → 2. 四维评分 → 3. 计算总分 → 4. 映射时间 → 5. 风险评估 → 6. 最终估算
```

## 📊 四维度评分表

### 维度1: 技术复杂度 (Technical)

| 分数 | 代码量 | 技术熟悉度 | 算法难度 | 集成难度 |
|------|--------|-----------|---------|---------|
| **1分** | <100行 | 非常熟悉 | 简单CRUD | 无集成或简单 |
| **2分** | 100-300行 | 基本熟悉 | 有业务逻辑 | 需要集成1-2个模块 |
| **3分** | >300行 | 不熟悉/需学习 | 复杂算法 | 需要集成3+模块 |

**快速判断**:
- ✅ 1分: "这个我做过很多次,轻车熟路"
- ⚠️ 2分: "这个做过类似的,但有些新东西"
- ❌ 3分: "这个没做过,需要查文档/学习"

### 维度2: 业务复杂度 (Business)

| 分数 | 业务规则 | 决策分支 | 状态数量 | 交互步骤 |
|------|---------|---------|---------|---------|
| **1分** | 简单明确 | <3个 | <5个 | <3步 |
| **2分** | 有一定复杂性 | 3-8个 | 5-15个 | 3-8步 |
| **3分** | 复杂,多重约束 | >8个 | >15个 | >8步 |

**快速判断**:
- ✅ 1分: "逻辑很直白,没什么分支"
- ⚠️ 2分: "有一些条件判断,但不复杂"
- ❌ 3分: "业务规则复杂,各种特殊情况"

### 维度3: 依赖复杂度 (Dependency)

| 分数 | 外部依赖 | 内部依赖 | 数据结构 | 时序要求 |
|------|---------|---------|---------|---------|
| **1分** | 0-1个 | 0-2个 | 简单对象/数组 | 无严格要求 |
| **2分** | 2-3个 | 3-5个 | 嵌套对象/复杂查询 | 有一定顺序 |
| **3分** | >3个 | >5个 | 多层嵌套/图结构 | 严格顺序+并发控制 |

**快速判断**:
- ✅ 1分: "基本独立,调1-2个接口就行"
- ⚠️ 2分: "需要协调几个模块,有点依赖"
- ❌ 3分: "涉及多个系统,依赖关系复杂"

### 维度4: 测试复杂度 (Testing)

| 分数 | 测试用例数 | Mock难度 | 边界情况 | 测试类型 |
|------|-----------|---------|---------|---------|
| **1分** | <5个 | 简单或无需 | <3个 | 仅单元测试 |
| **2分** | 5-15个 | Mock 2-3个 | 3-8个 | 单元+部分集成 |
| **3分** | >15个 | Mock >3个 | >8个 | 单元+集成+性能 |

**快速判断**:
- ✅ 1分: "测试很简单,几个用例就够了"
- ⚠️ 2分: "需要覆盖一些边界情况"
- ❌ 3分: "场景很多,需要全面测试"

## 🔢 综合评分与时间映射

### 计算公式

```
总分 = 技术复杂度 + 业务复杂度 + 依赖复杂度 + 测试复杂度
范围: 4-12分
```

### 时间映射表

| 总分 | 时间范围 | 任务类型 | 建议 |
|------|---------|---------|------|
| **4-5分** | 0.5-1h | 简单任务 | 直接实施 |
| **6-7分** | 1-1.5h | 中等简单 | 直接实施 |
| **8-9分** | 1.5-2h | 中等复杂 | 直接实施 |
| **10-11分** | 2-3h | 复杂任务 | ⚠️ 建议拆分 |
| **12分** | 3+h | 非常复杂 | ❌ 必须拆分 |

### 快速估算技巧

**经验法则**:
```
总分 ÷ 4 = 基础小时数
例如: 8分 ÷ 4 = 2h (上限)
```

**调整系数**:
- 熟悉的技术: × 0.8
- 不熟悉的技术: × 1.2
- 有参考案例: × 0.9
- 无参考案例: × 1.1

## ⚠️ 风险评估矩阵

### 风险等级判断

| 因素 | 低风险 🟢 | 中风险 🟡 | 高风险 🔴 |
|------|----------|----------|----------|
| **技术成熟度** | 成熟稳定 | 较新但有文档 | 未验证/实验性 |
| **团队经验** | 有丰富的经验 | 有部分经验 | 无经验 |
| **参考案例** | 有多个成功案例 | 有部分参考 | 无参考,需探索 |
| **影响范围** | 局部影响 | 模块级影响 | 系统级影响 |
| **回滚难度** | 容易回滚 | 可以回滚 | 难以回滚 |

### 风险应对策略

| 风险等级 | 缓冲时间 | 应对策略 |
|---------|---------|---------|
| **🟢 低风险** | +10% | 直接实施,常规测试 |
| **🟡 中风险** | +20% | 先做小规模POC,加强测试 |
| **🔴 高风险** | +50% 或拆分 | 必须先预研,分阶段实施 |

### 快速风险判断

**3个问题判断风险**:
1. "我之前做过类似的事情吗?" 
   - 是 → 低风险
   - 否 → 继续下一题

2. "团队其他人做过吗?有文档可以参考吗?"
   - 是 → 中风险
   - 否 → 高风险

3. "如果失败了,影响大吗?容易回滚吗?"
   - 影响小,易回滚 → 中风险
   - 影响大,难回滚 → 高风险

## 📝 评估示例

### 示例1: 简单任务

```markdown
任务: 创建User类型定义

技术: 1分 (TypeScript,非常熟悉,30行代码)
业务: 1分 (简单的数据结构定义)
依赖: 1分 (无外部依赖)
测试: 1分 (只需验证类型正确)

总分: 4分
估算: 0.5h
风险: 🟢 低

最终: 0.5h × 1.0 = 0.5h
```

### 示例2: 中等任务

```markdown
任务: 实现组合列表导出功能

技术: 2分 (需要使用exceljs库,200行代码)
业务: 1分 (业务逻辑简单,就是导出数据)
依赖: 2分 (依赖API接口和文件下载工具)
测试: 2分 (需要测试正常/空数据/大数据量)

总分: 7分
估算: 1-1.5h
风险: 🟡 中 (exceljs库使用经验有限)

最终: 1.5h × 1.2 = 1.8h → 取 2h
```

### 示例3: 复杂任务(需拆分)

```markdown
任务: 实现实时数据同步系统

技术: 3分 (WebSocket,不熟悉,400+行代码)
业务: 2分 (需要同步多种数据类型)
依赖: 3分 (依赖多个系统,复杂的消息队列)
测试: 3分 (需要全面的集成和性能测试)

总分: 11分
估算: 2-3h
风险: 🔴 高 (无WebSocket经验,影响面大)

决策: ❌ 超过2h且高风险,必须拆分

拆分方案:
- Task 1: 【预研】WebSocket技术方案评估 (2h)
- Task 2: 实现基础连接和心跳 (1.5h)
- Task 3: 实现数据订阅机制 (2h)
- Task 4: 实现数据同步逻辑 (2h)
- Task 5: 添加错误处理和重连 (1.5h)
- Task 6: 编写集成测试 (2h)
```

## 🚨 常见错误警示

### ❌ 错误1: 忽略学习成本

**症状**: 估算时假设自己对所有技术都熟悉

**修正**: 
```
问自己: "我真的用过这个技术吗?还是需要现学?"
如果需要学习,技术复杂度至少+1分
```

### ❌ 错误2: 低估测试时间

**症状**: 只估算开发时间,忘记测试

**修正**:
```
记住: 测试通常占20-30%的时间
复杂逻辑的测试时间可能更多
```

### ❌ 错误3: 过于乐观

**症状**: 只考虑理想情况,不考虑问题和调试

**修正**:
```
使用三点估算法:
(乐观 + 4×最可能 + 悲观) ÷ 6
```

### ❌ 错误4: 忽视沟通成本

**症状**: 假设可以专注编码8小时

**修正**:
```
实际有效编码时间: 6小时/天
预留时间给: 会议、讨论、代码审查
```

### ❌ 错误5: 一次性估算大任务

**症状**: 直接估算6-8小时的大任务

**修正**:
```
强制规则: 任何>2h的任务必须拆分
拆分为多个≤2h的小任务分别估算
```

## 💡 实用技巧

### 技巧1: 建立个人基准

记录你完成各类任务的平均时间:

```markdown
我的基准数据:
- Vue组件(简单): 1h
- Vue组件(复杂): 2h
- API开发: 1.5h
- Bug修复(简单): 0.5h
- Bug修复(复杂): 2h
- 单元测试: 1h/10用例
```

### 技巧2: 使用类比法

```
"这个任务和上周做的XXX很像"
→ 参考XXX的实际耗时
→ 根据差异微调
```

### 技巧3: 分解验证

```
对于不确定的任务:
1. 先分解为子步骤
2. 分别估算每个子步骤
3. 累加得到总时间
4. 如果>2h,就拆分任务
```

### 技巧4: 预留缓冲

```
永远不要按100%效率估算
至少预留20%缓冲时间
用于: 调试、意外问题、上下文切换
```

### 技巧5: 持续改进

```
每次任务完成后:
1. 记录实际耗时
2. 对比预估时间
3. 分析偏差原因
4. 调整估算策略
```

## 📈 准确率提升路径

### 第1周: 建立意识
- 开始记录所有任务的预估和实际时间
- 识别自己的估算偏差模式

### 第2-4周: 收集数据
- 积累至少20个任务的真实数据
- 按任务类型分类统计

### 第2个月: 形成基准
- 建立个人基准数据库
- 发现规律和调整系数

### 第3个月+: 持续优化
- 定期回顾和调整
- 分享经验给团队
- 建立团队基准
