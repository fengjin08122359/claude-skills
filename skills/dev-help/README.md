# Dev Help Skill

开发者助手和项目规划师技能,专门负责将开发需求拆分为2小时可完成的任务单元。

## 功能特性

- ✅ **智能需求分析** - 深入理解用户需求,识别模糊点
- ✅ **交互式信息收集** - 主动提问澄清不清楚的地方
- ✅ **任务拆解** - 将大需求拆分为2小时可完成的原子任务
- ✅ **任务确认机制** - 用户确认后才开始执行
- ✅ **进度管理** - 集成 progress-tracker 进行跨会话跟踪
- ✅ **分步执行** - 逐步推进并等待用户反馈

## 使用方法

### 自动触发

当你在对话中提到以下场景时,技能会自动触发:

- "我需要实现XXX功能"
- "帮我规划一下XXX的开发任务"
- "我要做XXX,应该怎么拆分?"
- "添加一个新功能XXX"
- "修复XXX bug"
- "重构XXX代码"

### 手动调用

你也可以显式调用:

```
@dev-help 我需要添加一个组合导出功能
```

## 工作流程

### 1️⃣ 需求分析阶段

技能会:
- 阅读你的需求描述
- 识别核心功能点
- 标记不明确的地方
- 向你提出具体问题

**示例**:
```
你: 我需要给组合管理页面添加导出功能

Dev Help: 
为了准确拆解任务,我需要确认几个问题:

1. 导出的数据范围是什么?
   - 当前视图显示的数据
   - 全部数据(不分页)
   - 用户自定义筛选的数据

2. Excel需要包含哪些列?
   - 所有列
   - 用户选择的列
   - 固定的核心列

3. 是否需要异步导出?
   - 数据量可能很大,需要后台生成后下载
   - 数据量小,可以前端直接导出

请回答这些问题,我会据此拆解任务。
```

### 2️⃣ 任务拆解阶段

技能会:
- 将需求拆分为2小时可完成的任务
- 定义每个任务的验收标准
- 标注任务依赖关系
- 估算总耗时

**输出示例**:

```markdown
# 组合导出功能开发任务计划

## 需求概述
为组合管理页面添加Excel导出功能,支持导出当前列表数据

## 技术方案
- 前端: 使用 xlsx 库生成Excel文件
- 后端: 提供数据接口,支持分页导出
- 权限: 需要export权限

## 任务列表

### Task 1: 设计导出API接口 (1h)

**描述**: 
定义导出接口的请求参数和响应格式

- [ ] 返回标准错误格式

### Task 2: 实现后端导出逻辑 (2h)

在组合列表页面添加工具栏导出按钮

- [ ] 按钮位置合理(工具栏右侧)

**依赖任务**: 无

### Task 4: 实现前端导出逻辑 (1.5h)

**描述**: 
实现前端调用API并触发下载的逻辑

**涉及文件**:

- `src/utils/fileDownload.ts` - 文件下载工具

**验收标准**:
- [ ] 能正确调用后端API
- [ ] 文件名格式正确(组合列表_20240101.xlsx)
- [ ] 支持取消导出操作

---

### Task 5: 编写单元测试 (1.5h)

**描述**: 
为导出功能编写单元测试

**涉及文件**:
- `__tests__/unit/exportService.spec.ts`
- `__tests__/unit/useCombinationExport.spec.ts`

**验收标准**:
- [ ] 测试覆盖率 > 80%
- [ ] 覆盖正常和异常场景
- [ ] Mock外部依赖
- [ ] 所有测试通过

**依赖任务**: Task 2, Task 4

## 总体估算
- 任务数量: 5个
- 预计总耗时: 7小时
- 关键路径: Task 1 → Task 2 → Task 4
- 可并行: Task 3可与Task 1/2并行
```

### 3️⃣ 任务确认阶段

技能会:
- 展示完整的任务列表
- 询问你是否有调整意见
- 根据你的反馈重新调整

**示例**:
```
我已将需求拆分为 5 个任务,预计总耗时 7 小时。

请确认:
1. 任务拆分是否合理?
2. 是否有遗漏的功能点?
3. 优先级是否符合预期?

如有调整意见,请告诉我具体需要修改的地方。
```

### 4️⃣ 逐步执行阶段

在你确认后,技能会:
- 调用 progress-tracker 初始化进度跟踪
- 按顺序执行每个任务
- 每完成一个任务向你汇报
- 等待你确认是否继续

**示例**:
```
✅ Task 1 已完成

进展总结:
- 完成了导出API接口设计
- 添加了ExportParams类型定义
- 通过了TypeScript类型检查

是否继续执行 Task 2: 实现后端导出逻辑?
或者需要调整后续任务?
```

## 任务评估体系

Dev Help 使用系统化的任务评估方法来确保时间估算的准确性。

### 四维度评估

每个任务从四个维度进行评估:

1. **技术复杂度** - 代码量、技术熟悉度、算法难度
2. **业务复杂度** - 业务规则、决策分支、状态管理
3. **依赖复杂度** - 外部/内部依赖、数据结构、时序要求
4. **测试复杂度** - 测试用例数、Mock难度、边界情况

### 评分标准

每个维度1-3分,总分4-12分:

| 总分 | 时间范围 | 建议 |
|------|---------|------|
| 4-5分 | 0.5-1h | 简单任务,直接实施 |
| 6-7分 | 1-1.5h | 中等简单,直接实施 |
| 8-9分 | 1.5-2h | 中等复杂,直接实施 |
| 10-11分 | 2-3h | ⚠️ 复杂,建议拆分 |
| 12分 | 3+h | ❌ 非常复杂,必须拆分 |

### 风险评估

同时评估风险等级:

- 🟢 **低风险**: +10%缓冲时间
- 🟡 **中风险**: +20%缓冲时间,先做POC
- 🔴 **高风险**: +50%缓冲时间或拆分为预研+实施

### 详细指南

完整的评估方法请参考:
- [任务拆解指南](references/task-breakdown-guide.md) - 详细的评估原则和方法
- [复杂度评估快速参考](references/complexity-assessment.md) - 快速查询表

### 2. 及时回答问题

当技能提出澄清问题时,尽量详细回答,这能帮助生成更准确的任务计划。

### 3. 认真确认任务列表

在任务确认阶段,仔细检查:
- 是否有遗漏的功能点

- 优先级是否合理
- 时间估算是否准确

如果发现任务计划不合理,随时提出调整:
- "Task 3和Task 4可以合并"

- "这个任务估计太乐观了,实际需要3小时"

## 常见问题

### Q1: 为什么每个任务限制在2小时?

**A**: 2小时是一个平衡点:
- 足够完成有意义的功能
- 不会太长导致难以估算
- 便于进度跟踪和调整
- 符合注意力集中周期

### Q2: 如果任务实际耗时超过2小时怎么办?

**A**: 这是正常的,2小时是估算值。如果明显超时:
- 暂停当前任务
- 分析超时原因
- 必要时重新拆解剩余工作
- 更新进度跟踪

### Q3: 能否跳过任务确认直接执行?

**A**: 不建议。任务确认是关键步骤:
- 确保理解正确
- 发现潜在问题
- 调整优先级
- 避免返工

但如果你非常确定,可以说:"不用确认,直接开始执行"

### Q4: 中途可以改变需求吗?

**A**: 可以。Dev Help 支持灵活调整:
- 暂停当前任务
- 说明新的需求
- 重新分析和拆解
- 更新任务列表

### Q5: 如何查看历史任务进度?

**A**: 通过 progress-tracker:

```
@progress-tracker 查看项目进度
```

会显示:
- 已完成任务
- 进行中任务
- 剩余任务
- 总耗时统计

## 技术细节

### 任务拆解算法

Dev Help 使用以下策略拆解任务:

1. **垂直切分** - 按功能模块拆分(优先)
2. **分层切分** - 按技术层次拆分
3. **用户故事切分** - 按用户操作流程拆分
4. **风险驱动** - 优先处理高风险部分

### 时间估算方法

- **三点估算法** - (乐观 + 4×最可能 + 悲观) / 6
- **类比估算** - 参考类似任务的历史数据
- **分解估算** - 拆分为子步骤分别估算

### 依赖关系分析

使用有向无环图(DAG)分析任务依赖:
- 识别硬依赖和软依赖
- 检测循环依赖
- 计算关键路径
- 确定并行机会
