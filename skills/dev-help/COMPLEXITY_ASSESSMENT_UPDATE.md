## 🎯 核心功能

### 四维度评估模型

每个任务从四个维度进行评估:

#### 1. 技术复杂度 (Technical Complexity)
- **评估因素**: 代码量、技术熟悉度、算法难度、集成难度
- **评分**: 1-3分
- **示例**: 
  - 1分: <100行,非常熟悉的技术
  - 2分: 100-300行,基本熟悉
  - 3分: >300行,需要学习新技术

#### 2. 业务复杂度 (Business Complexity)
- **评估因素**: 业务规则、决策分支、状态数量、交互步骤
- **评分**: 1-3分
- **示例**:
  - 1分: <3个分支,<5个状态
  - 2分: 3-8个分支,5-15个状态
  - 3分: >8个分支,>15个状态

#### 3. 依赖复杂度 (Dependency Complexity)
- **评估因素**: 外部依赖、内部依赖、数据结构、时序要求
- **评分**: 1-3分
- **示例**:
  - 1分: 0-1个外部依赖,简单数据结构
  - 2分: 2-3个外部依赖,嵌套对象
  - 3分: >3个外部依赖,复杂图结构

#### 4. 测试复杂度 (Testing Complexity)
- **评估因素**: 测试用例数、Mock难度、边界情况、测试类型
- **评分**: 1-3分
- **示例**:
  - 1分: <5个用例,简单Mock
  - 2分: 5-15个用例,中等Mock
  - 3分: >15个用例,需要集成测试

### 综合评分公式

```
总分 = 技术复杂度 + 业务复杂度 + 依赖复杂度 + 测试复杂度
范围: 4-12分
```

### 时间映射规则

| 总分 | 时间范围 | 任务类型 | 建议 |
|------|---------|---------|------|
| 4-5分 | 0.5-1h | 简单任务 | 直接实施 |
| 6-7分 | 1-1.5h | 中等简单 | 直接实施 |
| 8-9分 | 1.5-2h | 中等复杂 | 直接实施 |
| 10-11分 | 2-3h | 复杂任务 | ⚠️ 建议拆分 |
| 12分 | 3+h | 非常复杂 | ❌ 必须拆分 |

### 风险评估体系

#### 风险等级
- 🟢 **低风险**: 成熟技术,有参考案例,影响小
- 🟡 **中风险**: 较新技术,部分参考,模块级影响
- 🔴 **高风险**: 未验证技术,无参考,系统级影响

#### 缓冲时间
- 低风险: +10%
- 中风险: +20%,先做POC
- 高风险: +50%或拆分为预研+实施

## 📊 使用示例

### 示例1: 简单任务评估

```markdown
任务: 创建User类型定义

技术: 1分 (TypeScript,30行代码,非常熟悉)
业务: 1分 (简单的数据结构)
依赖: 1分 (无外部依赖)
测试: 1分 (只需验证类型)

总分: 4分
估算: 0.5h
风险: 🟢 低

最终: 0.5h × 1.0 = 0.5h ✅
```

### 示例2: 中等任务评估

```markdown
任务: 实现组合列表导出功能

技术: 2分 (exceljs库,200行代码)
业务: 1分 (业务逻辑简单)
依赖: 2分 (依赖API和下载工具)
测试: 2分 (需测试多种场景)

总分: 7分
估算: 1-1.5h
风险: 🟡 中 (exceljs经验有限)

最终: 1.5h × 1.2 = 1.8h → 取 2h ✅
```

### 示例3: 复杂任务(需拆分)

```markdown
任务: 实现实时数据同步系统

技术: 3分 (WebSocket,不熟悉,400+行)
业务: 2分 (多种数据类型同步)
依赖: 3分 (多个系统,消息队列)
测试: 3分 (全面集成和性能测试)

总分: 11分
估算: 2-3h
风险: 🔴 高 (无经验,影响面大)

决策: ❌ 超过2h且高风险,必须拆分

拆分方案:
- Task 1: 【预研】WebSocket技术方案 (2h)
- Task 2: 实现基础连接 (1.5h)
- Task 3: 实现数据订阅 (2h)
- Task 4: 实现同步逻辑 (2h)
- Task 5: 错误处理和重连 (1.5h)
- Task 6: 集成测试 (2h)
```

## 🎓 使用方法

### 方法1: 完整评估流程

适合重要任务或不确定时:

1. 阅读 [task-breakdown-guide.md](references/task-breakdown-guide.md)
2. 按照四维度逐一评分
3. 计算总分并映射时间
4. 评估风险等级
5. 应用缓冲系数
6. 得出最终估算

### 方法2: 快速评估

适合日常任务:

1. 打开 [complexity-assessment.md](references/complexity-assessment.md)
2. 查看速查表
3. 快速判断各维度分数
4. 查表得到时间范围
5. 根据风险调整

### 方法3: 使用模板

复制快速评估模板:

```markdown

**任务名称**: _______________

### 四维评分

- [ ] 业务复杂度: □1 □2 □3
- [ ] 依赖复杂度: □1 □2 □3
- [ ] 测试复杂度: □1 □2 □3

**总分**: _____ 分

### 时间估算
- 基础估算: _____ h

```

## 💡 最佳实践

### 1. 建立个人基准

记录自己完成各类任务的实际时间,形成个人基准数据库。

### 2. 定期回顾

每完成5-10个任务后:
- 对比预估和实际时间
- 分析偏差原因
- 调整估算系数

### 3. 分类统计

按任务类型统计准确率:
```
任务类型    | 平均偏差 | 调整系数
-----------|---------|----------
API开发     | -15%    | × 1.15
UI组件      | -25%    | × 1.25
Bug修复     | +10%    | × 0.9
```

### 4. 持续改进

- 记录每次估算和实际耗时
- 分析偏差模式
- 不断优化估算方法

## 🚨 常见错误

### ❌ 错误1: 过于乐观
**修正**: 使用三点估算法,预留缓冲时间

### ❌ 错误2: 忽视学习成本
**修正**: 诚实评估技术熟悉度,为学习预留时间

### ❌ 错误3: 低估测试时间
**修正**: 测试通常占20-30%,复杂逻辑更多

### ❌ 错误4: 忽略沟通成本
**修正**: 每天最多安排6小时实际编码

### ❌ 错误5: 一次性估算大任务
**修正**: 强制拆分为≤2h的任务
